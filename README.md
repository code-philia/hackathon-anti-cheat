# 竞赛智能体评审说明

本目录用于对竞赛选手提交的智能体代码进行两类静态评审。评审以 `example` 中的题目和 `workspace` 中的选手仓库为证据，不执行选手代码，不安装其依赖，也不访问选手代码中提供的外部 URL。

## 两个评审模块

### 核心策略分析

核心策略分析用于回答“这个智能体是如何生成作答结果的”。它追踪选手仓库中的入口、提示词、模板、skills、代码复用路径、模型适配器、工具调用、评测循环和状态保存机制。

分析覆盖八个方面：

- RAG/检索：索引、向量或关键词检索、任务指纹匹配，以及文件和上下文选择；
- 预置知识：提示词、技能、模板、示例、检查清单和领域规则；
- 代码复用：复制、解包、导入、补丁、已有应用和代码片段的复用；
- 提示编排：系统提示、用户提示、分阶段代理、任务拆分、上下文压缩和输出约束；
- 模型路由：模型端点、角色、备用调用、选择逻辑和结果组合；
- 工具与执行：文件读写、命令、浏览器、代码生成、构建和测试工具；
- 迭代与评测：计划、生成、检查、失败反馈、重试、修复和停止条件；
- 状态与持久化：缓存、摘要、快照、提交、运行状态和跨步骤上下文。

每个重要策略都需要说明状态、目的、输入或知识来源、选择方式、生成或使用方式以及输出，并为每一项提供选手仓库中的 `path:line` 定位。结论区分为：

- `confirmed`：代码和数据流可以直接证明；
- `inferred`：有多处证据支持，但部分运行路径是间接的；
- `unresolved`：存在相关证据，但关键文件、值或分支无法确认。

策略分析不是作弊判定。它可以记录代码复用或预置知识，但不会仅因发现模板、模型或相似文件就给出违规结论。

### 竞赛反作弊评审

反作弊评审用于判断选手仓库是否违反竞赛规则。它检查完整仓库中静态存在的代码、模板、提示词、归档文件和配置，并要求每个错误都有选手源代码的 `path:line` 证据。

主要评审标准包括：

- `TEMPLATE-DIRECT` / `TEMPLATE-INDIRECT`：预置材料是否直接或间接包含题目要求对应的完整实现、代码片段、功能约束、选择器、验收条件或领域合同；
- `MODEL-EXTERNAL`：模型 `base_url` 是否为允许的指定地址，是否存在额外 URL、API key 槽位或硬编码密钥；
- `MODEL-METER-TAMPER`：是否伪造、隐藏、删除或改写模型调用、用量或计费记录；
- `NET-EXTERNAL`：是否访问未经授权的外部网站、包服务、代码仓库，或平台提供的隐藏测试、评测器、期望输出等数据；
- `AC-INTERFERENCE`：是否通过注释、提示词、命令、混淆、输出处理或其他方式影响、误导或规避评审；
- `OTHER-SUSPICIOUS` / `INSPECTION-GAP`：规则之外的具体可疑行为，或确实无法检查的证据。

模板评审会区分普通通用框架和题目专用实现。构建配置、服务器启动、数据库连接、基础路由、静态资源处理等通常属于通用基础设施；登录、注册、搜索、筛选、排序、领域实体、指定页面状态、验收选择器和题目专用行为属于应用合同。将这类题目相关内容预先提供给生成流程，可能构成 `TEMPLATE-DIRECT` 或 `TEMPLATE-INDIRECT`。

反作弊结果使用两种判定：

- `错误`：证据满足明确规则，任何错误都会使初始结论为“作弊”；
- `警告`：存在具体但尚未解决的疑点，或有明确检查缺口；只有警告时初始结论为“通过”，供人工复核。

发现一个错误后仍需继续完成其他规则族的检查，不能因为已经足以判定就停止审阅。

## 评审结果目录

`result` 保存反作弊评审结果。每个选手通常对应一个 `.log` 文件，内容包括：

- 被审查的题目和选手工作区；
- 按规则编号组织的错误与警告；
- 原始仓库中的文件和行号证据；
- 对知识类型、选择方式、生成方式和适用范围的判断；
- 各规则族的覆盖声明；
- 最终的“作弊”“通过”或需要人工复核的结论。

同名的 `.trace.jsonl` 是评审过程的结构化执行记录，用于追踪调用、诊断和复核，不是最终裁决文本。

## 策略分析目录

`strategy` 保存核心策略分析结果。每个选手对应一个 `.log` 文件，内容包括：

- 智能体的主要端到端生成流程；
- 八个策略维度的逐项分析；
- 代码、模板、skills、提示词、模型和工具的来源及流向；
- 生成结果、检查结果、重试机制和持久化状态；
- 每项结论的证据位置和可信度标记。

此外，`strategy` 中的 `code-output-review-*.md` 文件用于复核 `agent` 与 `applications` 的关系：`agent` 是选手提交的智能体，`applications` 是其运行后的作答结果；报告通过压缩包内文件的 SHA-256 比对，区分模板、skills、依赖文件和完整业务代码是否逐字进入作答结果。

## 阅读结果时的边界

`strategy` 解释生成机制，`result` 判断规则风险，两者用途不同。最终 `applications` 中存在完整 GitHub 或 Sheet 应用，并不能单独证明其来源；需要结合 `agent` 中的模板、payload、blueprint、复制逻辑和文件级哈希证据判断。反过来，agent 中存在模板或技能也不自动等于违规，关键在于它是否包含题目专用实现，以及如何被选择并送入生成流程。
