ARC-Bench Agent Starter（Codex 版）
——一个让 AI 编程智能体按"需求树"自动开发 Web 应用的参赛样板

本项目是 ARC-Bench（AI 编程能力评测平台）上的"参赛智能体"：它读取一份以 ROOT 为根的需求树，把每个顶级子需求逐一交给 OpenAI Codex 智能体去实现，最终在输出目录中产出一个可运行的完整 Web 应用，并全程通过结构化数据向平台汇报进度、追溯与提交历史。

Python 3.10+ 编排层 Node.js / React / Express 应用层 53 个文件 · 约 0.42 MB 依赖 OpenAI Codex CLI 三大技能 + Python SDK
核心结论

这不是一个普通 Web 项目，而是一台"用 AI 写应用"的自动化流水线的控制端：main.py 是编排器，Codex 是执行写代码的 AI 程序员，template/ 是交给 AI 的"空白画布"，skills/ 与 arcbench-agent-runtime/ 是让 AI 按统一规范汇报工作（进度信号、需求追溯、git 检查点）的"仪表盘接口"，最终所有成果落到输出目录，并通过 .arc/ 下的 JSONL 事件日志与 JSON 追溯表让 ARC-Bench 平台实时可见、可评审、可回滚。

01

它是什么：一个"AI 写应用"评测赛的参赛智能体

ARC-Bench 是一种 AI 编程能力评测：平台给每个参赛智能体一份"需求树"（一棵描述目标应用的功能、场景、界面的层级清单），智能体要在有限次数内把它变成能跑的软件。本项目的全部代码，就是为这场评测准备的一个合格"选手"。

ARC-Bench 平台（考官）
准备需求树 requirements.yaml（id: ROOT）与权威模板，调用参赛智能体，之后根据产物与 .arc/ 数据评分
→
main.py（编排器 / 监考）
解析需求树 → 逐条拆任务 → 调用 Codex 会话 → 把每个需求子树变成真实代码
→
Codex（AI 程序员）
在同一个输出目录里连续修改代码；通过三个技能写进度、记追溯、打 git 检查点
三方协作示意：平台出题与验收，main.py 拆题与调度，Codex 动手实现

▍平台如何调用它（入口契约）

ARC-Bench 用一条命令启动本项目，三个环境变量由平台注入：

python3 main.py /path/to/requirements --output-dir /path/to/output --type web
输入
需求目录（含 requirements.yaml）
输出
--output-dir 下可运行 Web 应用
类型
--type web（默认 web）
注入变量
OPENAI_API_KEY / OPENAI_BASE_URL / MODEL

需求树长什么样：requirements.yaml 必须是含 id: ROOT 的映射，其 children 是若干"模块子树"，每个子树都带 id（如 REQ-1）、name、description、scenarios（场景与步骤）、children（下级需求）等字段。main.py 只把每个 ROOT 直接子节点当作一个待办模块。

关键设计：main.py 刻意不允许 Codex 读取完整 requirements.yaml，每次只下发一个子树的 JSON。既防止"偷看全卷"，也让每个模块任务更聚焦、可独立验收。
02

整体运作流程：八步把需求树变成应用

main.py 是整条流水线的唯一入口，从上到下依次执行：准备画布 → 装配工具 → 拆解任务 → 逐个交付。

1
平台准备输出目录ARC-Bench 已按权威模板 + 需求树（含演化基线）装配好 --output-dir；独立运行时则用本地 template/ 兜底
2
复制起步模板copy_template_contents()：把 template/ 的全部内容拷进输出目录（平台已备好时跳过，避免覆盖权威模板）
3
装配技能包copy_skills_to_output()：把 skills/ 复制到输出目录的 .codex/skills/，让 Codex 能找到三个工作技能
4
解析需求树load_root_modules()：校验 id=ROOT，把每个直接子节点包装成 RequirementModule（编号、总数、node_id、子树 JSON）
5
启动 Codex 会话thread_start()：工作目录=输出目录；沙箱=full_access（可自由改文件）；审批=deny_all（模型不得请求批准）；注入开发者指令
6
逐模块派活（循环）对第 i/N 个模块：把"该子树 JSON + 已完成的模块 id 列表"拼进提示词，调用 thread.run() 让 Codex 实现整个子树
7
Codex 在同一目录连续作业每个模块都在同一个输出目录改代码、装依赖、跑测试；全程可调用三个技能写进度信号、追溯记录、git 检查点
8
失败即停，成功收尾任一模 run() 返回 error 就抛 RuntimeError 中断；全部完成则返回 0，输出目录即最终可运行的应用 + .arc/ 数据
执行流程（橙色=循环派活阶段，灰色=结束条件）

▍每轮提示词里有什么

main.py 给 Codex 的每一条指令都是"菜单式"的：当前模块编号与名称、需求源目录、已完成的模块、技能所在目录、以及待实现子树的完整 JSON，最后要求"总结改动文件、不要启动长驻服务器"。开发者指令则固定要求 Codex：保留既有工作、不要读完整 requirements.yaml、优先用技能脚本而非手写事件 JSON。

04

起步模板：一张留给 AI 的"空白画布"

template/ 是一个功能完整的全栈 Web 骨架，但业务内容几乎为零——主页是空壳、数据库没有表、接口只有一个健康检查。这正是设计意图：模板负责提供"能跑起来的工程底座"，所有业务功能都留给 Codex 按需求树去填充。

▍技术栈一览

前端 frontend/

  • Vite 7 + React 19 构建
  • TypeScript 类型化源码（App / HomePage / api）
  • TailwindCSS 4 样式体系
  • React Router 7 路由（当前仅 "/" 一页）
  • axios 封装 /api 客户端
  • Vitest + Testing Library 前端测试

后端 backend/

  • Express 5 HTTP 服务
  • SQLite（sqlite3 驱动）本地数据库
  • cors + body-parser 中间件
  • /api/health 健康检查接口
  • 数据库工具集：建表 / CRUD / 种子 / 测试隔离
  • Vitest + supertest + Playwright 测试栈

单端口运行模式

  • 先 npm run build 构建前端到 frontend/dist
  • 后端同时托管 /api/* 与静态前端，并用正则做 SPA fallback（非 /api 的 GET 一律返回 index.html）
  • 前端未构建时，访问首页返回 503"Frontend build missing"提示页
  • 开发期 Vite 代理 /api 到后端端口，前后端可分进程热更

▍数据库工具集（backend/src/database/）

五个模块各司其职，全部遵循"幂等、可复用、集中管理"的约定，并给 AI 写好了使用指南注释
模块职责关键约定
init_db.js数据库连接生命周期与表结构初始化；支持切换/重建数据库文件建表用 CREATE TABLE IF NOT EXISTS；加字段用 ALTER TABLE 并做存在性保护
db_runtime.jsCRUD 封装（run/get/all/exec）+ withTransaction 事务助手所有读写统一走这里，不另起连接逻辑
seed_db.js幂等种子数据入口（INSERT OR IGNORE / UPSERT 语义）先父表后子表，fixture 保持最小
test_harness.js为测试创建隔离 SQLite 文件（.arc-test-db），含 setup/seed/reset/cleanup测试不得污染开发库
prepare_e2e.js为 Playwright E2E 准备独立数据库复用 test_harness 的运行时模式
对 AI 的"隐性考卷"：模板源码里到处是给 Codex 看的注释（如"Guide model instructions"），把数据库演进、种子、测试的规范直接写进代码——这保证了无论 AI 怎么写业务，工程地基都保持统一质量。
05

与平台的"数据契约"：.arc/ 下的三个通道

Codex 每写完一段代码，平台如何知道？答案在输出目录的 .arc/ 隐藏目录里。项目通过三条通道向平台交付"可审计的证据"。

事件日志.arc/runner-events.jsonl
追加式 JSONL：runner_state（运行生命周期）、requirement_state（需求各阶段状态）、signal（前端刷新信号）三类事件，平台据此渲染实时进度条与面板。
追溯台账.arc/traceability/*.json
7 张"表"以当前状态 JSON 存储：需求、场景、接口、测试、调用边、节点状态、节点契约，回答"哪个需求被哪些接口/测试覆盖、现在处于什么状态"。
Git 检查点git 提交历史
按阶段打提交（如 "REQ-2 (design): Search form interfaces"），供评审回滚；.gitignore 中保留 .arc/traceability 让追溯随代码一起回滚。

▍7 张追溯表（.arc/traceability/）

均为"主键 → 行"的 JSON 对象，写入采用临时文件 + 原子替换，读取即当前状态
表记录什么主键 / 关键字段
requirements需求节点（含名称、描述、视觉参考、场景、父子关系、依赖）req_id
scenarios需求场景（GIVEN/WHEN/THEN 步骤）scenario_id → req_id
interfaces生成的接口/UI 契约（类型、内容、文件位置、调用方/被调方、是否已实现）interface_id → req_ids[]
tests测试记录（类型、文件、关联接口、是否通过）test_id → req_id
call_edges需求/接口间的调用边（谁调用了谁）source::target::from::to 复合键
node_states每个需求节点当前状态（DESIGNING/DESIGNED/IMPLEMENTED/PASSED…）req_id
node_contracts节点级契约快照（自由结构 JSON）req_id

▍事件与刷新信号

事件写入 .arc/runner-events.jsonl，每行一个 JSON。其中 signal 事件带 refresh 标志位，告诉平台前端"哪个视图该刷新了"：submission（提交态）、logs（日志）、commit_history（提交历史）、traceability_selected / traceability_all（追溯视图）、preview（预览）。SDK 与技能每次写追溯或提交代码，都会自动补发对应信号，让平台面板"跟着动"。

06

三大技能：让 AI 按统一规范"汇报工作"

直接让大模型手写 JSONL 容易形状漂移、路径写错。因此项目把三类高频动作封装成三个"技能"，Codex 只需运行对应脚本，平台就能拿到格式稳定的事件。

三个技能都是"SKILL.md 说明 + CLI 脚本 + 参考文档"的结构，会被复制到 .codex/skills/ 供 Codex 使用
技能脚本用途典型命令
arcbench-runtime-signalsarc_signal.py报告运行生命周期（started/completed/failed/paused/resumed）、需求阶段（design/implement/test 的 started/done/failed）、前端刷新信号run-started / design-done / refresh
arcbench-traceabilityarc_traceability.py读写 7 张追溯表：存需求树、登记接口/测试、记录节点状态与契约、查询当前状态upsert-interface / upsert-node-state / list-tests
arcbench-checkpointarc_checkpoint.pygit 初始化与检查点：init、commit、status、head、reset、restore、clean，身份与 .gitignore 管理ensure-repo / commit / head

▍需求节点的状态机

进度信号最终汇成每个需求节点的状态，平台据此画进度。状态迁移如下（含平台预置的复合终态）：

UNSEEN→ DESIGNING→ DESIGNED→ IMPLEMENTING→ IMPLEMENTED→ PASSED
任一阶段失败→FAILED 全部子树收敛→CONVERGED 收敛但有失败子树→CONVERGED_WITH_FAILED_CHILDREN
需求节点状态机：主链为设计→实现→测试通过；任意环节失败即 FAILED；复合终态标记整棵子树收敛情况
使用纪律（写在 SKILL.md 里）：在"一个连贯阶段"结束后才打一次提交，不做每次文件写入都 commit 的碎提交；reset / restore / clean 属破坏性操作，只允许在显式暂停/回滚流程或用户指令下使用——防止 AI 拿回滚当"试错橡皮擦"。
07

arcbench-agent-runtime：Python 版"三合一"SDK

技能脚本是给"用命令行工作的 Codex"用的；SDK 是给"直接写 Python 的智能体"用的。二者逻辑同源：脚本里内联了与 SDK 几乎一致的实现，保证两条入口行为完全一致。

AgentRuntime.from_env() —— 从环境变量（ARCBENCH_OUTPUT_DIR 等）解析工作目录，一行代码拉起全套能力
聚合四个子组件，并自动把"事件 → 追溯表"的桥接接好（写进度事件时同步更新 node_states 表）
EventClient事件客户端
mark_design_done / mark_implementation_done / mark_test_passed 等，写 runner-events.jsonl 并触发状态与刷新信号
TraceabilityStore追溯存储
7 张表的完整 CRUD：存需求树、登记接口/测试、维护调用边、节点状态与契约，原子写入
GitClientGit 客户端
ensure_repo / commit / rollback / reset / restore / clean，确定性身份，自动管理 .gitignore 管理块
SDK 模块结构：RuntimePaths 负责路径解析，三个客户端各管一个通道，AgentRuntime 是唯一入口

▍一段代码看懂用法（examples/sdk_and_skill_usage.py）

runtime = AgentRuntime.from_env()          # 1. 拉起运行时
runtime.traceability.init_db()              # 2. 初始化追溯表
runtime.events.mark_design_done("REQ-1")    # 3. 报告"REQ-1 设计完成"
runtime.traceability.upsert_interface(...)  # 4. 登记接口 IF-LOGIN-API → REQ-1
runtime.traceability.upsert_test(...)       # 5. 登记测试 TEST-LOGIN-E2E
runtime.traceability.set_test_pass_status("TEST-LOGIN-E2E", True)  # 6. 标记通过
runtime.git.ensure_repo(create_initial_commit=True)   # 7. 初始化 git
runtime.git.commit("REQ-1 (design): Login") # 8. 打一个阶段检查点

    设计要点：值得借鉴的工程巧思

    每条要点都能在源码中找到对应实现
    设计做法收益
    模块级任务隔离只下发 ROOT 的一个直接子树 JSON，禁止读完整需求文件防作弊、聚焦实现、逐模块可验收
    同一目录连续作业所有模块共用同一输出目录，提示词明确"保留既有工作"模块天然衔接，应用保持完整可运行
    技能优先于手写 JSON指令要求用脚本，不手写事件/追溯 JSON事件形状稳定，路径解析一致
    确定性 git 身份环境变量 → 回退匿名身份，提交时统一注入作者/提交者提交历史可审计、可复现
    原子 JSON 写入写临时文件后 rename 替换，读失败返回默认空表追溯表不因断电/中断而损坏
    双入口同源SDK 库与技能脚本实现一致Python 智能体与 CLI 智能体行为统一
    全访问 + 拒绝审批Sandbox.full_access + ApprovalMode.deny_allAI 可自由写代码，但不能发起需批准的越权操作
    .arc 数据契约事件日志 + 追溯表 + git 提交三通道平台实时可见、可评审、可回滚，形成完整证据链
